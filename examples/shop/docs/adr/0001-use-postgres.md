# ADR-0001. Используем PostgreSQL как основное хранилище

## Статус

`accepted` на 2024-11-12.

## Контекст

Shop — e-commerce платформа с ACID-требованиями для заказов и платежей, сложными запросами по каталогу, поддержкой полнотекстового поиска и JSON для гибких схем (атрибуты товаров). Нужна основная реляционная БД.

Ограничения:
- должны храниться данные в РФ (152-ФЗ);
- нужна поддержка full-text search без отдельного сервиса;
- нужны JSON-поля для произвольных атрибутов товаров;
- нужна зрелая экосистема для миграций и ORM.

## Решение

Используем **PostgreSQL 16** как основное хранилище.

- ORM: EF Core 8.
- Миграции: EF Core migrations.
- Full-text search: встроенный `tsvector`.
- JSON: тип `jsonb` для атрибутов.
- Хостинг: managed Postgres в РФ (Yandex Cloud / аналог).

### Положительные последствия

- ACID из коробки.
- Зрелая экосистема, миграции, ORM.
- Full-text search без дополнительных сервисов.
- JSONB для гибких атрибутов товаров.
- Производительность на наших объёмах (10k RPS read) — более чем достаточна.

### Отрицательные последствия

- Вертикальное масштабирование ограничено (но на текущих объёмах не критично).
- Нужны DBA-компетенции или managed-сервис.

## Альтернативы

### MySQL 8

- Плюсы: знакомая команде, managed в любом облаке.
- Минусы: слабее JSON и full-text search, хуже для сложных запросов по каталогу.
- Почему не выбрали: каталог и атрибуты товаров — основной кейс, MySQL тут проигрывает.

### MongoDB

- Плюсы: гибкая схема, нет миграций.
- Минусы: ACID-транзакции в заказах — костыльно, нет зрелых миграций, нет full-text search на уровне PG.
- Почему не выбрали: заказы и платежи требуют строгой консистентности.

### ClickHouse

- Плюсы: отличная аналитика.
- Минусы: не OLTP.
- Почему не выбрали: не для основного хранилища. Рассматриваем для аналитики отдельно.
